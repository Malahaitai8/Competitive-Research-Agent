## 2. 重跑策略实验明细

| 策略 | 设计含义 | 运行耗时 | 搜索/抓取 | 语义问题变化 | 观察 |
| --- | --- | ---: | ---: | --- | --- |
| `0-cycle` | 只生成报告和风险提示，不做生成前材料补救，也不做生成后语义补救 | 86.121s | 0 / 0 | gaps 3 -> 3；unsupported 1 -> 1 | 成本低，但问题不会被修复。 |
| `1-cycle` | Evidence Gate 补救 + 最多一次语义补救 | 256.577s | 3 / 3 | gaps 3 -> 3；unsupported 0 -> 3 | 补救后 unsupported 反而增加，说明重写可能强化无证据结论。 |
| `2-cycle` | Evidence Gate 补救 + 最多两次语义补救 | 108.939s | 1 / 1 | gaps 0 -> 0 | 本次没有真正触发语义补救，不能证明两轮更好。 |
| `pre-only` | 只在报告生成前做 Evidence Gate 补救，生成后只标风险 | 104.740s | 1 / 1 | gaps 3 -> 3；unsupported 3 -> 3 | 生成前补救不能替代生成后语义检查。 |
| `post-only` | 生成前不补救，生成后做语义补救 | 138.791s | 1 / 1 | gaps 4 -> 10；unsupported 2 -> 5 | 初始证据弱时，生成后补救可能放大错误。 |

实验结论：

- 不能简单说“补搜两轮比一轮好”，因为本次 `2-cycle` 没有实际跑满两轮语义补救。
- 真正有价值的发现是：补救重写不是天然变好，可能把弱支撑内容改成更强但无证据的结论。
- 因此最终策略不是追求更多轮次，而是追求“每次补救都有净收益”。
- 当前生产默认策略为：最多一次受控 remediation cycle；补救后复检；复检变好才接受，变差则回滚。

## 4. 国内外短视频平台 badcase

任务口径：

| 字段 | 内容 |
| --- | --- |
| 研究主题 | 国内外短视频平台 |
| 竞品 | `tictok`、抖音、快手 |
| 研究维度 | 产品定位、目标用户、核心功能、会员价格、商业化方式、近期更新 |
| 地区 | 中国 |
| 时间范围 | 最近 6 个月 |
| 生成时间 | 2026-07-26 14:27 |

矩阵覆盖：

| 竞品 | found | missing | 说明 |
| --- | ---: | ---: | --- |
| `tictok` | 0 | 6 | 输入和矩阵里是 `tictok`，正文里是 `TikTok`，名称不一致导致矩阵无法对应。 |
| 抖音 | 6 | 0 | 虽然显示 found，但部分证据来自旧数据或低可信来源，不能代表质量合格。 |
| 快手 | 6 | 0 | 虽然显示 found，但近期更新和官方来源不足，部分 claim 支撑弱。 |

语义校验结果：

| 指标 | 数值 |
| --- | ---: |
| checked_items | 28 |
| supported | 3 |
| weakly_supported | 11 |
| unsupported | 14 |
| needs_human_review | 0 |
| semantic_gap_count | 19 |

关键 badcase：

- `tictok` 与 `TikTok` 没有做别名归一，导致矩阵里 TikTok 全部 missing，而报告正文却写了 TikTok。
- 抖音、快手部分结论依赖 2019-2020 年数据，不符合“最近 6 个月”口径。
- 快手近期更新缺失，但矩阵仍出现对应维度，没有明确标注“未找到公开资料”。
- 报告混入低可信来源，甚至出现不适合作为正式报告来源的站点。
- “会员价格”维度被广告收费、代运营收费等信息污染，和真正的平台会员体系混在一起。

已处理：

- 增加生成前的 `Competitor Normalizer` LLM 节点，不再靠静态词表穷举别名。
- 节点会让模型根据研究主题、竞品原始输入和常识判断 canonical name、aliases、confidence、reason。例如 `tictok` 是否应归一为 `TikTok`，`RED` 是否应归一为 `小红书`，由模型输出结构化结果决定。
- 只有置信度达到阈值的归一结果才会被接受；低置信度或歧义项保留原输入，并写入 `ambiguous_items`。
- 矩阵构建使用 canonical 竞品名，避免输入行名和正文称呼不一致。
- 竞品 alias map 会写入 metadata，后续矩阵抽取、语义校验和面试复盘都能看到“原始输入 -> 归一名称”的证据链。
- 对完全未知或模型不确定的新别名，系统不会强行改名，而是保留原输入并在后续语义校验里暴露缺口；这样可以避免把两个不同产品误合并。

补救结果：

- Semantic Validator 已经识别出 19 个语义 gap。
- Remediation Controller 进入 `1-cycle`，但没有拿到新增证据，所有补救动作降级为 `risk_only`。
- 这说明当前“检测”已经能发现问题，但“修复”受限于检索质量和主体规范化，没有足够证据时系统不会强行改写。

## 5. 为什么短视频平台效果差

这次不应该简单归因成“模型太差”，更准确是四类问题叠加：

| 问题类型 | 表现 | 影响 |
| --- | --- | --- |
| 输入规范化问题 | 用户输入 `tictok`，系统没有归一成 `TikTok` | 矩阵按原竞品名建表，正文按常见名写作，导致矩阵和报告断裂。 |
| 任务范围问题 | 用户说“国内外”，但结构化结果里地区是“中国” | 检索和报告容易偏国内，TikTok、YouTube Shorts、Instagram Reels 等海外平台覆盖不足。 |
| 检索来源问题 | DuckDuckGo 返回低可信、旧数据、广告代运营类页面 | 模型会拿到噪声证据，矩阵单元即使 found，也可能语义不对。 |
| 模型能力问题 | 当前复杂节点原先都使用 `deepseek-v4-flash` | flash 适合快速生成，但对复杂竞品别名、时间约束、证据一致性判断不够稳。 |

## 6. 模型调整记录

当前已将本地 `.env` 从“所有节点都用 flash”调整为：

```env
FAST_LLM=deepseek:deepseek-v4-flash
SMART_LLM=deepseek:deepseek-v4-pro
STRATEGIC_LLM=deepseek:deepseek-v4-pro
```

调整理由：

- `FAST_LLM` 保留 flash：用于轻量、快速任务，控制成本和响应速度。
- `SMART_LLM` 改 pro：报告写作、复杂总结和正文组织需要更强模型。
- `STRATEGIC_LLM` 改 pro：任务规划、Evidence Gate、Semantic Validator、Remediation 等节点更依赖推理和结构化稳定性。

需要注意：

- 换模型只能改善规划、写作和语义判断，不能单独解决检索源质量差的问题。
- 下一步更应该补：竞品别名归一、官方来源优先检索、低可信来源过滤、矩阵单元基于证据 ledger 生成，而不是只从报告里抽。

## 6.1 连接超时问题记录

现象：

- 新增 `Competitor Normalizer` LLM 节点后，单独验证时一度出现 120 秒超时。
- 日志表现为连续 `LLM request failed ... Connection error`。

定位结果：

- `api.deepseek.com:443` 直连可达。
- `Invoke-WebRequest https://api.deepseek.com` 能返回 401，说明网络到 DeepSeek 是通的。
- Python 进程环境里存在 `HTTP_PROXY/HTTPS_PROXY/ALL_PROXY=http://127.0.0.1:9`。
- httpx/langchain 会自动读取这些代理变量，导致请求走到本机 9 端口，从而连接失败。

修复：

- 增加代理环境清理：只清理 `127.0.0.1:9`、`localhost:9` 这类明显无效的 dead loopback proxy，不影响正常代理。
- 在服务启动和 LLM 调用前都执行清理。
- 给 `Competitor Normalizer` 增加快速失败策略：最多 2 次重试，每次 20 秒超时；失败后保留原竞品并写入 `ambiguous_items`，不阻塞整条研究链路。

验证：

- 真实 normalizer 调用成功：`tictok、抖音、快手` 被归一为 `TikTok、抖音、快手`。
- 本地服务重启后探活成功：`http://127.0.0.1:8000/` 返回 200。

## 7. 面试口径

可以这样讲：

> 我们做过 0-cycle、1-cycle、2-cycle、pre-only、post-only 的对照实验，发现补救重跑并不是轮次越多越好。某些情况下，重写会把弱支撑内容改成更强结论，导致 unsupported 增加。所以最终没有选择盲目两轮补搜，而是选择最多一次受控重跑，并加语义复检和回滚保护。  
>  
> 后续在“国内外短视频平台”这个 badcase 中，语义校验抓到了 19 个 gap，包括 TikTok 名称不一致、旧数据支撑近期口径、低可信来源混入、会员价格维度污染等问题。这个 case 说明检测链路有效，但修复效果受限于检索和主体规范化。因此我进一步把复杂 LLM 节点从 flash 换到 pro，同时计划补竞品别名归一和来源过滤。

## 8. 2026-07-26 补测与兜底逻辑整改总览

本轮整改围绕三件事展开：

1. 把竞品名称归一从静态写死规则改成 `Competitor Normalizer` LLM 节点。
2. 把生成后语义校验和补救重跑改成受控闭环：发现 gap -> 选择补救动作 -> 补搜/重写/标风险 -> 复检 -> 净改善才接受，否则回滚。
3. 处理 DeepSeek 连接超时和进度展示问题，避免任务卡在“正在收集资料并分析你的研究主题...”时没有明确反馈。

### 8.1 已实现逻辑

| 模块 | 本轮做了什么 | 设计原因 |
| --- | --- | --- |
| `Competitor Normalizer` | 新增生成前 LLM 节点，输出 `canonical_name / aliases / confidence / reason` | 解决 `tictok -> TikTok`、错拼、简称、中英文名不一致导致矩阵和正文断裂的问题，避免靠静态词表穷举。 |
| 归一结果落盘 | 将 `competitor_normalization` 写入 analysis JSON | 面试和排查时能看到“原始输入 -> 归一名称 -> alias map”的证据链。 |
| 矩阵构建 | 矩阵使用 canonical 竞品名和 alias map 匹配证据 | 避免正文写 `TikTok`，矩阵行仍叫 `tictok` 而全部 missing。 |
| Semantic Validator | 生成后检查矩阵单元和正文关键 claim | 生成前只能判断材料够不够，生成后才能判断最终写出来的内容是否被证据支撑。 |
| Remediation Controller | 不允许自由工具调用，只允许 `rewrite_only / search_and_rewrite / risk_only` | 控制成本、时延和错误传播，避免开放式 agent 随意多轮搜索。 |
| 复检与回滚 | 补救后重新校验受影响项，净改善才接受，变差回滚 | 实验发现重写可能让 unsupported 增加，所以必须有兜底。 |
| DeepSeek 超时处理 | 清理无效 `127.0.0.1:9` 代理；LLM 调用支持超时和重试 | 解决真实调用中 connection error / timeout 导致任务长时间卡住的问题。 |
| 进度展示 | 增加中文阶段、错误等级、raw message 保留 | 正常任务、重复提交、未知命令、语义校验失败、补救失败都应该在 UI 上有中文提示。 |

- 当前最大瓶颈已经从“名称对不上”转向“检索和证据质量不足”。

### 8.4 当前兜底策略

| 场景 | 当前处理 |
| --- | --- |
| 竞品名高置信度可归一 | 使用 canonical name 改写任务，并保留 alias map。 |
| 竞品名低置信度或歧义 | 保留原始输入，写入 `ambiguous_items`，不强行合并。 |
| 生成前材料不足 | Evidence Gate 诊断缺口，必要时材料补救。 |
| 生成后矩阵/正文 claim 不被证据支撑 | Semantic Validator 输出 `semantic_gaps`。 |
| 有证据但表达不稳 | `rewrite_only` 局部重写。 |
| 证据不足 | `search_and_rewrite` 受控搜索、抓取、抽证据，再局部重写。 |
| 公开资料不足或补救无效 | `risk_only` 标注待确认风险。 |
| 补救后变好 | 接受补救结果。 |
| 补救后不变或变差 | neutral 或 rollback，不让坏重写污染最终结果。 |

## 9. 下一步优化优先级

| 优先级 | 要做什么 | 为什么现在做 |
| --- | --- | --- |
| P0 | 官方来源优先检索和来源白名单 | 三个新 case 都说明矩阵覆盖可以满，但 official-like 来源不足会导致 claim unsupported。 |
| P0 | 搜索结果清洗：过滤 `/clev?...` 相对 URL、403、空内容、广告/低质站点 | 当前搜索/抓取经常拿到坏 URL 或低质量内容，浪费重跑成本。 |
| P0 | 补救 query 重写 | 现在补救有时拿 report 里的长 claim 当 query 搜，导致搜索噪声很大。应该把 gap 转成短、精准、官方源优先的 query。 |
| P1 | 矩阵从 evidence ledger 生成，而不是主要从报告正文反抽 | 可以减少“报告写偏了，矩阵也被带偏”的问题。 |
| P1 | 进度展示端到端压测 | 用户实际遇到过卡在收集资料阶段，需要确保超时、搜索失败、补救失败都有中文错误。 |
| P1 | 扩充评测集 | 增加 AI 搜索、短视频、AI 对话助手、AI 视频、本地生活等 10-20 条 case，用同一指标跑回归。 |
| P2 | 2-cycle 只保留为深度模式或实验对照 | 现有数据不支持生产默认两轮，且两轮成本和误修风险更高。 |

面试口径：

> 本轮迭代后，我们把“报告生成前材料门控、生成后语义校验、受控补救重跑、复检回滚”串成了闭环。实验上，名称归一类 badcase 有明显改善，比如 `tictok -> TikTok` 后矩阵覆盖从 12/18 到 18/18，另一个未出现在提示词示例中的 `perplexcity -> Perplexity` 也能正确归一。但补救重跑不是万能的，AI 搜索产品 case 中补救虽然新增了来源，但复检没有净改善，所以系统选择回滚。这说明我们的策略不是盲目重跑，而是用语义复检决定是否接受补救。下一步重点会放在官方来源优先检索、坏 URL 过滤和补救 query 重写上。

### 10.4 最终效果结论

- 名称归一有效：`tictok -> TikTok`、`perplexcity -> Perplexity` 这类错拼、别名、大小写问题可以由 LLM 归一节点处理，矩阵行名和正文主体不再断裂。
- 重跑机制有用，但它的价值不是“必然改好报告”，而是“发现问题、尝试受控补救、复检、无净改善则不接受”。这避免坏重写污染最终报告。
- P0 后补救搜索更受控：从长 claim 搜索改成短 query，坏 URL 不进入抓取和分析，第三方博客不再被误算成官方来源。
- 本轮端到端报告质量没有稳定提升。最新 AI 搜索产品复测中，Perplexity、Wikipedia 多次超时，`metaso.cn` 能命中但正文过短，补救没有新增可用证据，所以 Semantic Validator 把大量内容判为 `needs_human_review`。
- 因此当前最真实的结论是：闭环机制已经更可控、更可解释，但瓶颈已经从“是否会检查和重跑”转移到“检索器和抓取器能否稳定拿到高质量官方证据”。

### 10.5 面试口径补充

可以这样讲：

> 我们不是简单堆更多重跑轮次，而是做了对照实验和 badcase 复盘。实验发现，重跑如果没有复检和回滚，可能把弱支撑内容改成更强但无证据的结论，所以生产策略选择默认最多 1 个受控 remediation cycle。这个 cycle 包含 gap 诊断、受控搜索或局部重写、复检、接受或回滚。后续在 AI 搜索产品 badcase 里，我们进一步发现问题不只在模型，而在检索和抓取质量：官方 URL 能被找到，但经常 403、超时或正文过短。因此我们收紧了 URL 清洗、官方来源计数和补救 query 重写。最终系统能更诚实地暴露“证据不足”，而不是为了生成完整报告去编结论。
