# 项目讲课笔记

## 讲课主线

1. 项目定位与整体功能：这是一个面向竞品/行业调研的 Agent，不是单纯 AI 工具调研器。
2. 用户输入与任务规划：把结构化调研需求转成可检索、可写作、可评估的研究任务。
3. 检索、抓取与证据整理：搜索网页、抓取正文、抽取证据，并形成后续报告和矩阵可用的材料。
4. 报告与竞品矩阵生成：围绕竞品和研究维度生成报告正文、对比矩阵和来源列表。
5. 评测与迭代模块：通过分层用例、指标和 badcase 复盘推动系统从“能生成”走向“可解释可信度”。
6. Agent 设计与闭环：Evidence Gate、Semantic Validator、Remediation Controller、复检和回滚。
7. 产品体验与工程兜底：进度展示、错误提示、下载、历史记录、风险提示。
8. 面试逐字稿整理：把项目背景、方案设计、关键难点、指标和反思串成面试表达。

## 第五讲：评测与迭代模块

### 核心讲法

- 评测模块不是为了汇报“跑了多少 case”，而是为了证明系统经过 badcase 驱动迭代后，主场景效果更稳定。
- 项目评测对象是通用竞品/行业调研 Agent，因此不能把口径写成“AI 工具调研 Agent”。AI 搜索、AI 办公、AI 编程只是主测场景，外卖、旅游、短视频、Agent 产品等用于验证泛化和暴露边界。
- 评测指标分两类：
  - 自动指标：报告结构完整率、矩阵覆盖率、来源分级、官方来源覆盖、时间范围风险、语义 gap 数量。
  - 人工抽样指标：关键事实是否被来源支撑、引用是否真的对应 claim、结论是否过度外推。
- 简历指标要保守表达：主场景深测中结构完整率稳定在 90% 以上，矩阵覆盖率由典型 badcase 的约 67% 提升到 90% 以上；不要把 3 条深测的 98% 包装成全量系统准确率。

### Badcase 与迭代

- 矩阵单元格内容重复：说明矩阵抽取不能只做关键词命中，需要检查竞品 x 维度是否真的对应。
- 竞品名不一致：如 `tictok -> TikTok`、`perplexcity -> Perplexity`，说明需要 LLM 竞品名称归一，而不是写死别名字典。
- 官方来源不足：搜索结果可能是 CSDN、知乎、导航站、旧文章，因此需要来源分级、官方 profile、坏 URL 清洗和官方来源风险提示。
- 补救可能变差：补救重写可能强化无证据结论，因此需要候选改写、来源质量过滤、语义复检和 neutral/rollback。
- 信息时效性风险：报告可能混入 2025 年信息，不一定满足“最近 6 个月”口径，因此需要时间范围 warning。

### 用户被绕住的问题

- “100%/98% 是否太夸张”：是，样本量小且主要是自动指标，简历应写 90% 以上和典型 badcase 改善，不写成全量准确率。
- “为什么不强调 AI 场景”：因为产品定位是通用调研 Agent，AI 只是主测样例。
- “重跑为什么还要回滚”：因为搜索/抓取/重写都可能引入新问题，复检决定是否接受补救。
- “只生成候选改写是什么意思”：补救节点先写草稿修正版，不直接覆盖最终报告，通过独立复检后才合并。

## 第六讲：Agent 设计与闭环

### 核心讲法

- 这个项目的 Agent 不是开放式“想调什么工具就调什么工具”的自由 Agent，而是围绕竞品调研流程设计的受控研究流水线。
- 设计目标不是让 Agent 显得复杂，而是把竞品调研拆成稳定、可检查、可回滚的阶段：任务规划、检索抓取、证据整理、生成前材料门控、报告生成、生成后语义校验、受控补救、复检和风险标注。
- 生成前的 `Evidence Gate` 只判断材料是否够写，不判断最终报告是否写对。
- 生成后的 `Semantic Validator` 才检查最终矩阵和正文 claim 是否被证据支撑。
- `Remediation Controller` 不允许自由多工具调用，只允许白名单动作：`rewrite_only`、`search_and_rewrite`、`risk_only`。
- 补救结果不是直接覆盖报告，而是候选改写；复检后有净改善才接受，否则 neutral/rollback，并把未解决项展示为可信度提示。

### 为什么这么设计

- 竞品调研天然有多步流程，如果让模型一次性“搜、读、写、判断”，可控性差，也很难定位 badcase。
- 生成前检查和生成后检查职责不同：材料够不够写，与最终写出来是否被证据支撑，不是同一个问题。
- 受控补救能限制成本和错误传播：比开放式自由 Agent 更容易解释、评测和回滚。
- 复检/回滚来自实验事实：补救重写可能把弱支撑内容改成更强但无证据的结论，所以必须让独立校验决定是否接受。

### 面试表达

可以这样讲：

> 我没有把系统设计成完全开放式工具调用 Agent，而是按真实竞品调研流程拆成受控闭环。生成前用 Evidence Gate 判断材料是否足够，生成后用 Semantic Validator 检查矩阵单元和正文 claim 是否被证据支撑。如果发现 gap，Remediation Controller 只允许局部重写、补搜后重写或风险标注三类动作。补救结果先作为候选改写，经过复检确认有净改善才合并，否则回滚并展示未解决风险。这样做的好处是成本可控、错误可追踪，也能向用户解释报告可信度。

### 补充解释

- Evidence Gate 材料不足时会触发生成前材料补救，相当于再搜一轮，但 query 会围绕具体竞品、维度和官方来源生成，不是盲目泛搜。
- `neutral` 表示补救执行了，但没有带来净改善，也没有明显变差。系统通常保留原结果，并把未解决问题标注为风险。
- `accepted` 表示复检后确认补救有净改善；`rollback` 表示补救后变差，需要回滚候选改写。

## 第七讲：产品体验与工程兜底

### 核心讲法

- 竞品调研 Agent 的用户体验不只是“最后有没有报告”，还包括任务执行过程是否透明、失败时是否可理解、结果风险是否能被用户看见。
- 进度展示、错误提示、风险提示和矩阵可读性，都是可信度体验的一部分。
- 如果任务卡在“正在收集资料”很久，用户不知道是在搜索、抓取、LLM 等待还是失败，会直接降低信任。
- 如果日志中英文混杂、错误漏报，用户会以为系统无响应或结果不可控。
- 如果矩阵单元格内容重复、颜色难读、风险提示像装饰胶囊，会影响用户对报告质量的判断。

### 主要优化点

- WebSocket 进度事件统一字段：`stage / status / severity / message_zh / raw_message / duration_ms`。
- 前端对常见英文日志做中文归一化，保留 raw message 供调试。
- 错误和普通日志分层展示：重复提交、未知命令、搜索失败、语义校验失败、补救失败都要有明确中文提示。
- UI 阶段按用户理解展示：任务解析、搜索抓取、材料门控、材料补救、报告生成、语义校验、补救重跑、结果保存。
- 风险提示不应该只做彩色胶囊；高亮文本可以改成清晰的小清新颜色和加粗，提升可读性。
- 矩阵单元重复不是纯 UI 问题，背后是矩阵生成/抽取没有真正区分竞品 x 维度，需要回到语义校验和矩阵抽取逻辑处理。

### 面试表达

可以这样讲：

> 我把产品体验也纳入了 Agent 可靠性设计。因为调研任务耗时长，如果用户只看到一个加载态，很难判断系统是在正常搜索、抓取失败还是 LLM 卡住。所以我统一了 WebSocket 进度事件，给每个阶段加中文状态、错误等级和原始日志；同时在结果页展示官方来源不足、时间范围风险、低可信来源占比等提示。这样用户不仅拿到报告，还能理解报告生成过程和可信度边界。

## 第八讲：代码架构与模块落点

### 核心讲法

- 面试时不能只讲概念，还要能说清楚“用户请求进来后，代码里哪些模块负责什么”。
- 这个项目可以按前端、API 层、研究执行层、竞品分析层、评测与补救层、结果存储层来理解。
- 前端负责收集结构化调研需求、展示进度、展示报告/矩阵/风险提示。
- API 层接收 `/report/` 请求，创建研究任务，处理同步/异步执行和 WebSocket 日志。
- 研究执行层负责规划 query、搜索、抓取、整理上下文和生成报告。
- 竞品分析层负责把最终报告和过程 metadata 转成 analysis JSON，包括竞品矩阵、来源分级、语义校验和风险提示。
- 补救层负责 Evidence Gate、受控搜索补救、Semantic Validator、Remediation Controller 和复检回滚。
- 结果存储层负责 Markdown、Word、JSON、历史记录和下载。

### 关键文件

- `frontend/`：用户界面、调研表单、进度展示、结果展示。
- `backend/server/app.py`：FastAPI 应用入口。
- `backend/server/websocket_manager.py`：WebSocket 连接和日志推送。
- `backend/server/progress_events.py`：进度事件标准化、中英文日志归一。
- `backend/server/competitive_research.py`：竞品分析后处理，生成矩阵、来源分级、风险提示和 analysis JSON。
- `backend/server/agent_repair.py`：Evidence Gate 和生成前材料补救。
- `backend/server/semantic_validation.py`：生成后语义校验。
- `backend/server/semantic_remediation.py`：语义补救、候选改写、复检和回滚。
- `backend/server/competitor_normalization.py`：竞品名称归一。
- `gpt_researcher/actions/query_processing.py`：任务拆分和 query 规划。
- `gpt_researcher/actions/web_scraping.py`：网页抓取入口和坏 URL 过滤。
- `gpt_researcher/competitive_sources.py`：官方来源 profile、来源分级、URL 清洗。
- `evals/` 和 `outputs/`：评测任务定义、真实运行结果和实验记录。

### 面试表达

可以这样讲：

> 从代码结构上，我把系统拆成请求入口、研究执行、竞品分析、质量校验、补救闭环和结果存储几层。前端提交结构化调研需求后，后端 API 创建研究任务，研究执行层负责规划 query、搜索抓取和生成报告；报告完成后，竞品分析层会生成矩阵、来源分级和风险提示；如果材料或语义支撑不足，会进入 Evidence Gate 和 Semantic Validator 驱动的补救闭环；最终报告、矩阵和 analysis JSON 会一起保存，供前端展示和后续评测复盘使用。
